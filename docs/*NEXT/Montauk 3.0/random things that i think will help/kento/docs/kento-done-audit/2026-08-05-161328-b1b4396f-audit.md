# Kento done audit - 2026-08-05

**Commit audited:** `4894c741a7d35a14dfcb1442778af8b3220fbdb5`

**Verdict: NOT DONE.**

The ordinary suite is stable in the environments exercised, but the required
standard is stronger: the tests must be error-free, detect meaningful
regressions, and run without human oversight. Kento currently fails all three
parts of that standard:

1. The CI sensitivity command is broken at HEAD.
2. A mutation that changes observable behavior survives all 82 tests.
3. No unattended CI execution is currently verifiable or reachable from this
   checkout.

No product, test, workflow, or tool file was left modified by this audit. Only
this report was added.

## Blocker 1: the CI sensitivity job fails at HEAD

Running the exact workflow command:

```text
python3 tools/mutation-gate.py
```

produced:

```text
CAUGHT         33 cases
AMBIGUOUS(0)   app: leave the merged report unsorted
caught 33/34 viable mutants
exit 1
```

The stale case at `tools/mutation-gate.py:130-133` searches for adjacent
`rust_checks(...)` and `diagnostics.sort()` lines. The current implementation
has `shell_checks(...)` between them at `src/app.rs:480-482`, so the named
snippet occurs zero times.

`.github/workflows/ci.yml:49` runs this script unchanged. The sensitivity job
would therefore be red even if CI were connected today. This is an error in the
test tooling itself, not a hypothetical coverage concern.

## Blocker 2: a killable mutant survives the complete suite

The full current sweep was re-run over all 514 enumerated sites:

| Verdict | Count |
| --- | ---: |
| Caught by unit tests | 330 |
| Caught by integration tests | 109 |
| Caught by timeout | 33 |
| Uncompilable | 34 |
| **Survived** | **8** |

The raw score is therefore **472/480 viable mutations, or 98.3%**.

At least one survivor is not equivalent:

```text
src/install.rs:367
!file_type.is_file() || file_type.is_symlink()
                         changed to
!file_type.is_file() && file_type.is_symlink()
```

An isolated probe created a FIFO as a hook-state record:

| Build | Observed result |
| --- | --- |
| Current code | exit 2 immediately: `kento: malformed hook state record` |
| Surviving mutant | blocked in `read_to_string`; killed after a 2-second timeout |

All 82 tests remained green for that mutant. A FIFO is a valid Unix filesystem
entry, and returning an error versus hanging indefinitely is plainly observable
behavior. A test can create the FIFO and enforce a timeout exactly as the probe
did.

`docs/kento-equivalent-mutants.md:33-37` acknowledges that the FIFO diverges,
then dismisses it because reading it blocks. Blocking is the regression, not a
reason to exclude the input. The repository's claim that every killable mutant
is killed is therefore false.

Two other survivors are also described using race assumptions rather than
semantic equivalence:

- `src/app.rs:451`: the first metadata lookup can fail and the lookup in
  `discover` can then succeed.
- `src/toolchain.rs:103`: a shell file can change or become unreadable between
  discovery and `names_zsh`.

Those may require deterministic fault injection, but they cannot honestly be
called equivalent merely because the observable window is narrow.

## Blocker 3: the tests do not run without human oversight

`git remote -v` is empty, and there are no remote refs. There is no verifiable
CI run for current HEAD and no configured destination to which a push from this
checkout could trigger the workflow.

Every result in this audit was produced because a human initiated it. That is
the opposite of the stated unattended requirement. The written workflow is not
evidence of automation until it executes, and Blocker 1 means its sensitivity
job would currently fail.

## High: the full mutation proof is not an enforceable gate

The mechanical sweep has several errors that make it unsuitable for unattended
trust:

1. `tools/mutation_sweep.py:265` defaults to stop index `453`, while the current
   population is `514`. A normal no-argument run silently omits 61 sites,
   including all six `maintenance.rs` sites, all 15 `toolchain.rs` sites, all
   eight `types.rs` sites, and 32 tail sites in `lint.rs`.
2. `tools/mutation_sweep.py:229-231` converts harness exceptions into
   `ERROR(...)` records, but `:327` still returns exit 0.
3. The sweep also returns exit 0 when survivors exist. This audit observed eight
   survivors and `script_exit=0`.
4. `tools/mutation_recheck.py:96` likewise returns exit 0 even when mutations
   still survive or evaluation errors occur.
5. CI does not run the full sweep. It runs only 34 hand-written cases, one of
   which is already stale.

The reported 98.3% is a manually interpreted measurement, not an automated
quality gate. It can go stale, skip files, encounter harness errors, or retain
survivors while still reporting shell success.

## High: the tests themselves are not tested

`tools/mutation_sweep.py` lists only production files and stops scanning each at
`#[cfg(test)]`. It does not mutate unit-test bodies, integration tests, test
helpers, the CI workflow, or the mutation tools. The 34-case gate mutates only
production source as well.

This audit found a stale mutation-gate case precisely because no layer verifies
the verification tooling. Product mutation testing is useful evidence that
tests detect selected product changes; it is not proof that the tests
themselves contain no errors.

## High: the maintenance surface is incomplete in integration coverage

No integration test invokes `maintenance` or `kento:maintenance`.

Concrete omissions:

- `reports_every_usage_error_with_its_own_message` omits
  `kento maintenance bogus`, despite covering the corresponding uninstall
  argument error.
- The installed-command assertion at `tests/integration.rs:1239-1251` omits
  `kento:maintenance`, although `src/install.rs:8-21` installs it.
- The orchestration in `maintenance()`, including its `rustup` calls and public
  command output/exit behavior, is not exercised end to end.

The operator-only sweep does not delete an alias string or remove a command arm,
so its score does not close these gaps.

## Medium: CI is not fully reproducible

The workflow uses mutable `actions/checkout@v4`, floating
`ubuntu-latest`/`macos-latest` images, and whatever ShellCheck version those
images happen to contain. Rust and the Cargo lockfile are pinned, which is good,
but the workflow comment claiming reproducibility is broader than the actual
pinning.

This is secondary to the blockers: the workflow has not run, and its current
sensitivity command already fails locally.

## Required before the word "done" is supportable

1. Fix or replace the stale mutation gate and make its exact CI command pass.
2. Add a FIFO hook-state test; reclassify the survivor and re-run all 514 sites.
3. Make sweep bounds derive from the current population and return nonzero for
   survivors, missing records, stray processes, or `ERROR(...)` outcomes.
4. Run that complete gate automatically rather than relying on a manually
   interpreted report.
5. Add integration coverage for the maintenance command, usage error, and
   installed alias.
6. Add verification of test and harness changes, not only product mutations.
7. Connect the repository to CI and inspect a green run of current HEAD on every
   declared platform.

Until those are complete, Kento's ordinary tests are promising but cannot be
trusted completely.
